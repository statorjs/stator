Images are part of Stator. Declaring `images: { dir }` in `stator.config.ts` mounts an image endpoint over the directory: the URL's extension is the delivery format (request `x.webp?w=800` of a stored `x.jpg` and the server converts and resizes to honor it — never `Accept`-header or user-agent negotiation), widths come from an allowlist, variants cache on disk, and every response carries an ETag with bodyless 304 revalidation. Transformation runs through a swappable `ImageTransformer` adapter with sharp as the lazy-loaded default — an unconfigured app mounts no routes and never loads it.

Rendering ships on the `components` subpath: `<Image>` emits CLS-safe markup (`width`/`height` always present, `srcset` over the endpoint, lazy + async defaults), `<Picture>` adds modern-format `<source>` chains with the stored format as fallback, and `getImage()` is the pure resolver beneath both. Dimensions are required, always, and come from data: probe them once at upload with `probeImage()` and store them — renders are synchronous and never do image IO. Remote URLs render untouched and require dimensions like everything else; GIFs render as originals only, and SVG serves as an originals-only passthrough too (no resizing, no rasterizing, no fabricating an SVG from a raster), with every SVG response carrying `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` plus `nosniff` so an uploaded file's embedded scripts are inert on direct navigation.

Cropping is one word in one vocabulary: `crop` is a ratio (`1` square, `16 / 9` widescreen) the endpoint cover-crops to via `?w=&h=`, and the emitted `width`/`height` describe the *cropped* result, so the reserved box matches the pixels that arrive. Both axes stay allowlisted — widths from `images.widths`, ratios from `images.aspectRatios` (square, 4:3, 3:2, 16:9 and portrait duals by default) — so photographic crops work while the variant space stays finite, and a ratio the endpoint would reject is a render error rather than a silently dropped source. `<Picture sources>` is for geometry that *varies by breakpoint* (art direction: each entry crops under its media condition, crossed with every format including the stored one, and overrides the component-level crop there); a single fixed geometry like a thumbnail grid is just `crop` on the component. Component srcsets and crop validation read the resolved config from the render state, so markup can't drift from what the endpoint accepts.

Loading control decomposes. `priority` remains the one-word LCP escape hatch (`loading="eager"` + `fetchpriority="high"`), but the attributes it stands for — `loading`, `fetchpriority`, `decoding` — are settable directly with their native names and values, because the rollup assumes a hero and a thumbnail grid wants its whole first row eager with only the first at high priority. The shorthand and its constituents are mutually exclusive in the types, so `<Image priority loading="lazy">` fails to typecheck instead of resolving silently.

Validation is by content, not coincidence: ETags are a hash of the original's bytes — strong for originals, weak (`W/"…"`) for variants, whose bytes may drift across encoder upgrades while the pixels stay the same. Reseeding or copying media no longer busts every visitor's cache (mtime is demoted from identity to a memo key), a changed original busts correctly at the next revalidation, and a variant's `If-None-Match` answers `304` before any encode runs — even if the variant was never encoded at all. The freshness policy is a dial: `images.maxAge` (default `0` — every use revalidates), `images.staleWhileRevalidate` (render instantly from cache, revalidate in the background), and `images.immutable` (appends the no-recovery marker to a long maxAge; only for apps whose image URLs are write-once by construction). EXIF orientation is handled end-to-end too: transforms bake rotation into the pixels (re-encoding drops the tag, so without this every variant of a portrait phone photo came out sideways), and `probeImage` reports *display* dimensions for transposing orientations, so stored width/height — and the CLS box rendered from them — are never sideways either.

Encoding stays inside its host's means. `images.threads` caps the libvips worker pool (sharp's default is the host's *reported* core count, which on a shared-cpu host can fan a single AVIF encode out across 8+ threads of demand on a fractional vCPU); `images.encodeTimeoutMs` (default 15s, `0` disables) degrades a request past deadline to a `302` at the stored original instead of blocking, while the encode keeps running to fill the cache for the next visitor; `images.concurrency` (default 2) bounds how many cold-cache transforms run at once across all requests, on top of the per-path stampede dedup that already prevents duplicate encodes; and AVIF encodes at effort 2 instead of sharp's default of 4 — effort is a CPU-vs-density trade, not a visual-quality knob, and an on-demand endpoint has a real visitor waiting on the encode.

The design was proven end-to-end in `examples/indie-blog` before promotion; the example migrates onto this surface in a follow-up.
