What an island's script does with a machine import decides what its bundle gets. Since 3.0.0-next.4 every module importing `defineMachine` became a `{ name }` stub in an island bundle, wherever it lived, so `cart = use(Cart)` with a `defineMachine` machine passed `stator check` and threw in the browser, and no machine with real states could run client-side. Now the bundle gets the machine's code when the script passes the import to `use()`, directly, through a `const` alias, or as what a machine factory returns (`const Menu = makeToggle('Menu')`), and the module's code when the script reads a named export or a property other than `name`. It gets the `{ name }` that `dispatch()` addresses, and none of the machine's code, when the script only dispatches to the import or reads its `name`. Nothing marks a file as client or server: one definition can be registered on the server, run in an island and tested in Node, in an app island and in a library island through `build:lib` alike, including a machine under `machines/`.

`build:lib`'s browser-safety check accepts `@statorjs/stator/machine`, the entry a machine is defined from, in a published client entry.

Three things now fail instead of shipping: a machine import the script uses in a way the build cannot place (handed to another function, put in an array, re-exported, reached through a barrel file), located at its line; a server-pinned machine passed to `use()`, naming what pins it (`reads machine "Prices"`), the gate the docs described and nothing enforced; and server code reached from an island's bundle. `stator dev` shows them in the overlay on save and keeps serving the last good build, `stator check` reports them without bundling, and `stator build` applies them when it bundles. `build:lib` keeps the type-only named imports of a machine import it stubs. `use()` given a stub throws a message naming the machine, and in dev the file it came from, instead of a `TypeError`.
