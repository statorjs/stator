## What and Why

`Image`/`Picture` (spec `images-are-part-of-stator-*`) shipped as plain `.ts` function components, copying the `JsonLd` precedent directly — nobody re-litigated the choice. Testing them in a real app exposed the gap: they should be real `.stator` components (scoped styles as needed, composed the same way any other component is), with `getImage()` staying a pure, publicly-exported helper for custom art direction — Astro's actual split (`getImage()` vs. `<Image>`/`<Picture>` as real `.astro` files), not the `JsonLd` shape.

That ran into a real wall: `@statorjs/stator` (and any third-party package) cannot ship raw `.stator` source inside `node_modules`. Both `dev-native.ts` and the production build treat `node_modules` as a deliberately opaque, already-resolved boundary — load-bearing for correctness, not an oversight (`toolchain-adapter-seam-and-the-vite-exit`: versioning/transforming framework internals pulled from a dependency risks forking singletons across versions; `?v=` propagation "MUST stop at node_modules" for the same reason). So a `.stator` component library has to pre-compile to plain `.ts` before publish, the same way Svelte/Vue component libraries have long had to.

Pre-compiling exposed a second, deeper gap. Scoped CSS delivery today is pure static source-scanning: `dev-native.ts`'s `scanAll()` and production's `build.ts` both walk raw `.stator` *text* in the app tree, re-run the compiler fresh, and concatenate every file's CSS into one `components.css` — aggregated by presence in the directory tree, not by whether the component is ever imported or rendered. A pre-compiled library component has no `.stator` source left for that scan to find, so naively "fixing" this by having a library ship one aggregate `dist/components.css` is itself wrong: importing one `Button` would pull in CSS for every component the library ships, used or not.

Auditing this surfaced that the identical flaw already exists for apps' own components, today, in shipped production builds: `scanAll()`/`build.ts` include CSS for every `.stator` file sitting anywhere in the app tree, regardless of whether it's actually reachable from any route. Every app built with Stator today ships every component's styles on every page. That's a real correctness bug independently of anything about component libraries, and this spec fixes both with one mechanism — they're the same problem (presence-driven aggregation instead of usage-driven aggregation) wearing two costumes.

A first cut of "usage-driven" risked under-shooting the actual bug: computing one shared, app-wide `components.css` (every component used *anywhere* in the app, still one file on every page) kills truly-dead components but doesn't stop page A from loading page B's styles. The real fix is per-route CSS — each route gets an artifact scoped to only the components *that route's* template can reach. That in turn raises a sharper question, resolved against `conditional-arm-interiors-are-second-class-on-the-live-update-path` (shipped): a `match`/`when`/`each` arm that is inactive at first paint can still become active later purely via an SSE live-update patch, with no fresh HTTP request — so "reachable" must mean static reachability (everything the route's compiled template imports, including every conditional arm's and island's components), never "what actually rendered for this response." Render-tracing would starve an inactive arm's component of CSS at first paint and reproduce, class-for-class, the invisible-styling bug the `:global()` paper-cut already caught (no console error, no build failure, just wrong pixels once the arm flips). See Constraints.

## Scope

**1. One compile-and-emit-sibling-pair operation, used by both the app's own production build and a library's publish step.** `build.ts` already compiles every local `.stator` file to `${file}.ts` ahead of deploy and already computes `result.css` per file (`build.ts:165-186`) — it just currently throws that per-file CSS away into one concatenated `components.css`. Change the last step only: write `${file}.css` as a sibling of `${file}.ts` instead of accumulating into one blob. A library's publish-time compile is then literally the same operation — `compile()` per `.stator` file, `.ts` + sibling `.css` written out — run over the library's own source instead of an app's, with its output exposed via `package.json`'s `exports` map. No new manifest format, no second implementation to maintain — one operation, two call sites.

  > **Revised (2026-10-02).** This originally assumed each published component gets its OWN exports subpath (`${componentSpecifier}.css` per component) — true of the synthetic test fixture it was validated against, false of `@statorjs/stator` itself, which publishes `Image`/`Picture`/`getImage`/`getPicture`/`JsonLd`/etc. through one combined `./components` barrel. A bare specifier resolves to the whole barrel, not a component, so there is nothing for a per-component `.css` lookup to key off. Fix: the publish step ALSO aggregates one `components.css` for the barrel's own entry point (`entryCss()`, the same walk `routeCssMap` does for a route, rooted at `components/index.ts` instead — see `scripts/compile-components.ts`), published as its own `"./components.css"` export. This trades true per-component granularity for simplicity at the barrel level: importing `Image` currently also pulls in `Picture`'s CSS, and vice versa, within that one subpath. Acceptable while the barrel holds a couple of components; the fix if it grows a lot more is per-component subpath exports, each with its own `.css` — not done now, no consumer has asked for it, and it's a bigger public-API surface change.

**2. Route-level, usage-driven CSS aggregation in production, with zero branching on component origin.** Once local production output and library output are the same shape (compiled module + sibling `.css`), the aggregator doesn't need to know or care where a reachable component came from. Walk each route file's own import graph **separately** — not one combined esbuild pass with per-entry attribution; genuine per-route granularity is cheaper as N small walks, mirroring the existing `routeIslandMap`/`walkImports` pattern (`islands.ts`) already used for per-route island reachability — following relative imports (resolved and recursed, bounded to the app root) and bare specifiers (recorded, resolved once for their own sibling `.css`, never traced further into `node_modules`). Every component that route's template reaches — including everything reachable only inside a `match`/`when`/`each` arm or behind an island; see Constraints — contributes its sibling `.css` if one exists. One route, one artifact, one algorithm, no "if local / if external." `build/head.ts` links each route's own artifact instead of the one global `/static/components.css` constant. This retires `scanAll()`'s walk-by-*presence* entirely (replaced by walk-by-*reachability*) — closing the pre-existing over-inclusion bug as a side effect of this change, not a separate effort.

**3. Dev-native stays genuinely different, and that's fine.** Dev has no shipped-payload-size pressure and its whole value is compiling local `.stator` source on demand without a batch build step — so it keeps calling `compile()` fresh per local file and reading the sibling `.css` export for `node_modules` components, accumulating into one evolving `/static/components.css`, same ergonomics as today. It never does per-route splitting, so it never needed the production side's uniform-shape simplification in the first place; the two pipelines are allowed to work differently because they're solving different problems (iteration speed vs. shipped payload size), not because of an arbitrary local/external split.

  > **Revised (2026-10-02).** This paragraph described the intended dev-native behavior from the start, but the `node_modules` half was never actually built in the same pass as Scope items 1–2 — `dev-native.ts` kept pruning `node_modules` entirely, same as production used to, until a dogfooding pass (adding a real style to `<Image>`) caught the gap live. Now actually true: `dev-native.ts` tracks bare specifiers reached across the app's module graph (`externalSpecs`, built alongside the existing local-import graph in `updateEdges`) and folds each one's resolved sibling CSS into `/static/components.css` via `externalCss()` — the same resolution production uses, just accumulated into dev's one file instead of split per route.

**4. First real consumer: `getImage()`/`getPicture()` + `<Image>`/`<Picture>`.**
- `images.ts` keeps only pure helpers — `getImage()`, a new `getPicture()`, the shared types, and the format/crop/mime-type math (`SOURCE_TYPES` and friends) — all exported publicly so custom art-direction components aren't locked out.
- `Image.stator`/`Picture.stator` become real `.stator` components, compiled through the new publish step, holding the markup. `Picture.stator` composes `<Image>` as a JSX tag (the way `product-card.stator` composes `<Plate>`), not a function call.
- Neither ships a `<style>` block at launch — neither has a current styling need. The point of this spec is proving the capability and the pipeline end-to-end, not adding presentation nobody asked for.

  > **Revised (2026-10-02).** "Proving the capability" without ever exercising it is exactly the failure mode a feature like this invites — a scoped-styles pipeline nobody has run a real style through can be broken in ways no test happens to cover. `<Image>` now carries a real `<style>` block (the responsive-image baseline: `display: block; max-width: 100%; height: auto`), migrated out of `examples/indie-blog`'s global `app.css`, which had carried an explicit comment admitting the gap ("the framework `<Image>` carries no styles of its own"). The app keeps only what's actually its own aesthetic layering (border-radius, margin) under the same selector. This is what caught the barrel-aggregation gap in Scope item 1 and the dev-native gap in Scope item 3 — both dormant until a real style existed to expose them.

## Constraints

- "Reachable" means static reachability from a route's compiled template/import graph — every component the route *could* render, including one sitting only inside an inactive `match`/`when`/`each` arm or an unmounted island — never execution-tracing of what actually rendered for a given request. A route's artifact must not be narrowed to first-paint-visible components only: `conditional-arm-interiors-are-second-class-on-the-live-update-path` (shipped) establishes that an inactive arm can become active later via an SSE live-update patch with no fresh HTTP request, so its component's CSS has to already be present at first paint. This is a floor on how small a route's CSS artifact can get, not a bug in the design — do not "optimize" it later by tracing rendered output instead of the static graph.
- The production aggregator (Scope item 2) must not branch on component origin. If an implementation needs an `isExternal`/`isLocal` check to decide how to fetch a reachable component's CSS, that's a sign Scope item 1 wasn't done — local output and library output must already be the same shape (compiled module + sibling `.css`) by the time the aggregator runs.

## Out of scope

- A general, documented third-party `.stator` component-library ecosystem — authoring guides, scaffolding, a public second example library. This spec proves the mechanism using `@statorjs/stator`'s own `components` subpath as the only real consumer.
- Any change to how `.stator`/JS module resolution treats `node_modules` — that opacity invariant (`toolchain-adapter-seam-and-the-vite-exit`) is untouched; this is purely a CSS side-channel layered on top.
- CSS-in-JS-style runtime embedding (compiled module exports its CSS as a string constant, collected at render time). Considered and rejected: it trades a single static, cacheable `components.css` for either per-response cost or a build-time trace that ends up walking the same import graph this spec already walks, for no real benefit over a plain sibling file.
- Redesigning client-script/island CSS scoping (`descendant` strategy). Out of scope unless the graph-walk change is found to break it — verify, don't redesign.

## Success Criteria

- A library publishes a `.stator` component; an app importing only that one component gets only that component's CSS, PROVIDED that component has its own exports subpath — true of the synthetic test fixture, not of `@statorjs/stator`'s actual combined `./components` barrel, where importing one component currently pulls in the whole barrel's CSS (see Scope item 1's revision). The production aggregator code still contains no conditional on whether a reachable component is local or from `node_modules` — verified by code review, not just behavior — the granularity gap is a property of how many exports subpaths a library chooses to publish, not a branch in the aggregator.
- Two routes importing non-overlapping component sets (mix of local and `node_modules` components) produce two different CSS artifacts, each containing only its own route's reachable set — not the library's/app's whole component inventory.
- A component used only inside an inactive `match`/`when` arm at first paint still has its CSS present in that route's artifact (regression test: render the route, simulate the live-update flip that activates the arm, assert no missing styles — mirrors the `conditional-arm-interiors` regression pattern).
- A test app with an intentionally-unused `.stator` component (present in the tree, never imported by any route) ships a build with no route artifact containing that component's styles — closing the pre-existing bug.
- `getImage`/`getPicture` remain plain, pure, publicly exported functions; `<Image>`/`<Picture>` are real `.stator` components, importable and composable the same way any other `.stator` component is.
- An app using no library components keeps the SAME TOTAL set of component CSS it had before, just reorganized into per-route files instead of one shared `components.css` — not literally byte-identical output (per-route splitting changes the artifact layout by design, for any app with more than one route), but no content lost or duplicated incorrectly relative to today's aggregate.
- A real styled component, consumed by a real app through `node_modules`, reaches that app's production build AND its dev server, and a sibling route in the same app that doesn't use the component ships none of its CSS. Not a synthetic fixture — verified against `examples/indie-blog`'s actual `<Picture>` usage and a route (`routes/admin.stator`) that has none. See Implementation Notes.

## Open Questions

- Shared-chunk dedup across routes (two routes both using a common `Nav` component currently means duplicate CSS bytes in each route's artifact) — likely fine for v1 given scoped CSS is small per component, but worth a follow-up if payload size becomes a real complaint.
- Does the production metafile walk need to treat dynamic `import()` (island/client-script boundaries) differently from static imports, or does existing island bundling already resolve this the same way? (Note: the walk ended up regex-based, mirroring `routeIslandMap`, not an esbuild metafile — see Scope item 2's current text.)
- Per-component exports-subpath granularity for `@statorjs/stator`'s own `./components` barrel (Scope item 1) — not pursued now, revisit if the barrel grows enough that pulling in a sibling component's CSS becomes a real complaint rather than a theoretical one.

**Resolved, removed from this list:**

## Implementation Notes

Landed on `feature/stator-component-libraries-scoped-css` (not yet merged):

- **Scope 1 & 2** (`packages/stator/src/build/compile-component.ts`, `route-css.ts`, `build.ts`, `build/head.ts`): per-route CSS aggregation shipped, origin-blind as specified — `route-css.ts`'s `routeCssMap` has no `isLocal`/`isExternal` branch. Verified against a synthetic `node_modules` fixture built at test time (`tests/route-css.test.ts`) and against the real `fixtures/build-app` app (`tests/build.test.ts`): the index route (reaches a styled component) gets its own CSS artifact, the stepper route (reaches none) gets no stylesheet link at all.
- **Scope 3** (dev-native): initially left unchanged by design, as written — but "unchanged by design" turned out to mean "the `node_modules` half was never actually built," not "deliberately deferred." Fixed once a real style existed to expose the gap (see below): `dev-native.ts` now tracks bare specifiers per app file (`externalSpecs`) alongside its existing local import graph, and `regenCss()` resolves each one's sibling CSS via `externalCss()` into the dev aggregate. Covered by `tests/dev-native-external-css.test.ts` — a real subprocess `stator dev` against a fixture that imports the REAL `@statorjs/stator/components` (resolved through this package's own self-referencing `node_modules` symlink, not a synthetic stand-in).
- **Scope 4** (`getImage`/`getPicture`/`<Image>`/`<Picture>`): `getPicture()` + `SOURCE_TYPES` added as public helpers. `<Image>`/`<Picture>` converted to real `.stator` components (`src/components/image.stator`, `picture.stator`), which forced building the publish-time compile step (`scripts/compile-components.ts`, `pnpm build:components`, wired into `prepublishOnly`) ahead of schedule — turned out to be a hard prerequisite, not a nice-to-have, since a consuming app's production build never traces into `node_modules` to compile anything, including this package's own components. `components/index.ts` imports the compiled `.stator.ts` sibling directly, never the raw `.stator` source.
- **Live-update-arm regression test** (Success Criteria, item 3) added: `tests/route-css-arm.test.ts` + `tests/fixtures/route-css-arm-app/`. A machine-bound `match()` whose initial state renders the `loading` arm (plain text, no component) while the `ready` arm renders a styled `Badge` component. Builds the fixture, confirms the served HTML never rendered `Badge` (`Loading`, not `Ready`), and confirms the route's CSS artifact contains `Badge`'s `.badge` rule anyway — proving reachability is reachability, not render-tracing, through the real build pipeline rather than just unit-testing `routeCssMap` in isolation. Passed on first run, as expected from the walk being static by construction.
- **Transitive local cascade** (`tests/route-css-cascade.test.ts`): a 3-deep local chain (route → component A → component B → component C, each importing the next, each with its own sibling CSS) contributes every level's CSS to the route — `reachableFrom`'s recursion was already transitive by construction, this just proves it rather than leaving it asserted.
- **`<Image>` dogfooded with a real style**, closing out the "neither ships a `<style>` block yet" gap this section used to note. That single change surfaced two real, previously-undetected gaps — both closed, both covered above:
  - `@statorjs/stator` publishes its components through one combined `./components` barrel, not one exports subpath per component — the per-component `${specifier}.css` convention (Scope item 1) had only ever been proven against a synthetic fixture shaped with per-component subpaths. Fixed by aggregating one `components.css` for the whole barrel at publish time (`entryCss()`, rooted at `components/index.ts`), published via a new `"./components.css"` export. Full writeup in Scope item 1's revision note.
  - dev-native's missing `node_modules` CSS handling (Scope item 3, above).
  - **A CSS specificity trap**, caught by the user reviewing the actual shipped selector rather than just the passing tests: `scopeCss`'s per-element strategy appended `[data-s-h]` AFTER a `:where(...)` subject (`:where(img)[data-s-h]`, specificity (0,1,0)) instead of inside it (`:where(img[data-s-h])`, specificity (0,0,0)) — `:where()`'s entire reason to exist is always-zero specificity, so appending outside it silently defeated the whole point: a bare single-class app override would only win if it happened to land later in the document, not reliably. `styles.ts`'s `attachScopeAttr` now special-cases a `:where(...)` subject and recurses the attribute into each of its own arguments instead. `<Image>`'s baseline uses `:where(img)` for exactly this reason. Covered by three new cases in `compiler-styles.test.ts`.
  - **Self-referential CSS growth**, caught immediately after by actually reading `components.css`'s content rather than just its byte count: `route-css.ts`'s regex-based specifier scanner never stripped comments, so `json-ld.ts`'s own entirely normal doc-comment usage example (`*   import { JsonLd } from '@statorjs/stator/components'`) was read as a real import. Harmless anywhere the resolved target was something else, but here it resolved to `components.css` ITSELF — so every `pnpm build:components` run read the previous run's stale on-disk output as newly "reached" and appended it again, growing without bound. Fixed with a string/template-literal-aware comment stripper applied before scanning (`stripComments`). Covered by a new case in `route-css.test.ts`; verified empirically (two consecutive runs produce byte-identical output).
- **Verified end to end against `examples/indie-blog`** (the one real `<Picture>` consumer in the workspace), for real, not just via unit tests: its dev test suite and a full production build both pass; the Image CSS is confirmed present in the production build output (`dist/static/css/routes/posts/[slug].stator.css`, `dist/static/css/routes/index.stator.css`) and in the dev server's live `/static/components.css`, in both cases resolved through the actual `node_modules` symlink via the new `./components.css` export, with the fixed zero-specificity selector; `examples/indie-blog/static/app.css`'s `article img.u-photo` rule now carries only the app's own aesthetic layering (border-radius, margin), with a comment explaining the split. As a negative control: `routes/admin.stator` (no `<Image>`/`<Picture>` usage) was confirmed to ship a route CSS artifact with its own legitimate styles but ZERO bytes of the Image CSS — the original bug, demonstrated fixed in a real app, not just a fixture.
- All Success Criteria now met on this branch, including the granularity caveat on item 1 (see its text) and the new real-app verification item. Three real bugs surfaced and fixed purely by dogfooding a real style through the pipeline (barrel aggregation, dev-native, specificity, self-referential growth — four, really) that no synthetic fixture or unit test happened to cover — the dogfooding instruction that drove this was not a formality.
